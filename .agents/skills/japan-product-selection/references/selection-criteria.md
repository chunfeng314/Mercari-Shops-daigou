# 日本选品规则与实现现状

本文件保存会影响候选取舍、且需要随项目证据迭代的规则。更新时写清哪些是用户指定的硬条件、哪些是当前实现状态、哪些只是排序参考。

## 当前业务硬条件

- Mercari 商品售价必须 **> 9,999 JPY**，即最低 10,000 JPY。9,999 日元不合格；价格未知或无法确认币种也不合格。
- 关键词发现优先处理有效在售商品。同行店铺扩展中，已售商品是重要的历史需求证据，可以保存为选品种子；必须标明已售，不能当作当前日本在售货源。后续创建上架资料前，要另查当前日本价格参考。
- 保存的商品必须可以回到原始日本商品页面核验。不要仅凭搜索摘要、图片相似或同系列描述编造型号、版本、套装数量、成色或库存。
- 选品阶段只证明日本站存在符合条件的候选。中国站同款、现货、价格、图像使用权和利润需要后续阶段单独核验。

其中“> 9,999 日元”是用户在本项目提出的硬门槛，除非用户明确更新，不因个别搜索结果调整。对在售商品，此门槛检查当前标价；对已售商品，只能检查页面保留的历史标价，不能将其称为成交实付金额，除非页面有明确证据。价格筛选代码位于 `app/modules/japan_selection/mercari.py`：`MINIMUM_PRICE_JPY = 10_000`，`has_eligible_jpy_price` 以及 `filter_minimum_price`；对应测试位于 `tests/test_management.py`。

## 候选排序参考

先过滤硬条件，再比较仍合格的候选。优先考虑：

1. **身份可识别**：标题、图像和详情能对应到明确品牌/系列/型号/版本/规格，组合商品的数量说得清楚。
2. **后续找货可检索**：名称包含稳定的商品名、品牌或型号，能够转换成中国平台常用的商品识别信息。只把它作为搜索可行性的判断，不等于已找到中国货源。
3. **市场信号有证据**：仅记录页面实际展示的销量、收藏、评价或同类成交信息，附来源页面与采集时间。没有信号就记未知，不因为售价高推断需求强。
4. **歧义与交易风险较低**：优先单一明确规格、图片与文字一致的条目。盲盒、随机款、多规格页、成套与单品混卖、附属配件易混淆的商品，应标出具体歧义；若目标款价格无法确认，不放入合格候选。

排序可用“高 / 中 / 低”描述，并给出证据，不要伪装成精确概率或利润预测。正常任务无需等待用户逐条批准；对不满足硬门槛的候选直接排除，对证据不完整但仍可继续查找的候选标明风险。

## 搜索与核验

- 日本站查询用日语商品名与日本站页面真实用词。中文主题先确认品牌的日文官方名、系列名或页面常见叫法，再分别组合品牌、系列、型号、限定版、地区限定及商品类型等词。
- 至少尝试宽泛词与识别度更高的组合词；根据结果中的真实标题补充同义写法。记录实际查询，减少重复和过长查询造成的漏搜。
- 从搜索卡片读取候选后打开原商品页核对标题、价格、链接、售卖状态和图片。多规格商品若卡片价格是“起价”，需要打开选项并确认目标规格对应价格；无法确认时排除该目标款。
- 规范化链接并去重。已存在于本地项目记录的商品不重复导入。
- 页面遇到登录、短信验证、验证码、安全拦截或网络故障时，按失败类型记录并停止该站点任务；不要将错误页解释成搜索无结果，也不绕过验证。

## 同行店铺网络发现模式

把一个商品候选作为种子，沿着商品和卖家的关系扩展：

1. 从种子商品页记录卖家主页链接与卖家标识；打开卖家商品页，采集可访问的在售和已售商品。
2. 依据店铺中多个不同商品的标题、详情、品牌/系列和商品图，判断其是否长期经营中国相关商品。需要证据来自商品组合，而不是仅凭卖家所在地、单件商品或账号名称推断。记录判定依据与强弱，不把“日代同行”当成已验证的卖家自述。
3. 将店铺商品逐条规范化为产品身份。先按同款聚合不同商品页和不同卖家，再分别保留各条 listing、售卖状态、页面价格、时间和卖家关系；不同版本、套装数量、规格或配件不能错误合并。
4. 已售 listing 贡献历史需求证据；在售 listing 贡献当前价格和可观察供给证据。同款若多个卖家均有已售记录，作为更强的重复需求信号。标价不等于成交金额，已售页面也不证明现在还有货。
5. 把符合门槛、身份可识别的商品计划加入中国找货候选；将仍有歧义或价格未过门槛的条目留作研究节点并记录原因。对高相关商品继续发现其他卖家，逐步扩展候选网络。

网络记录至少应表达以下关系：`卖家 --发布--> listing`、`listing --指向--> 规范化商品`、`已售 listing --证明--> 历史需求`、`商品 --关联--> 新卖家/搜索词`。同一个商品可以连到多个卖家，同一个卖家可以连到多个商品；不要把店铺与单条 listing 混作一条记录。

规模控制应通过队列、分页、唯一卖家/商品去重和每轮处理上限完成，并保留未处理的扩展节点供下轮继续。目标是系统性规划卖家商品组合，不是单轮无限抓取。发现模式、种子链接、卖家主页、listing 状态和关系证据都要保留来源。

## 当前代码覆盖范围

- `app/site_catalog.py` 列出 Mercari、Yahoo!オークション、ラクマ、Yahoo!フリマ和 2nd STREET，但目录并不代表全部已实现。当前 `app/modules/japan_selection/mercari.py` 是实际 Mercari 公开页面采集器；`app/modules/japan_selection/adapter.py` 仍只是待接入站点的接口约定。接入新站后，先验证页面结构、价格、状态和重复数据，再把站点加入可执行流程。
- Mercari 搜索默认限定 `on_sale`，价格解析优先读取商品卡片标题/价格节点并可从详情页 JSON-LD 读取资料。卡片采集还会返回 `sold` 标志；导入任务不应只依赖价格过滤，必须同步检查售罄标志。
- 当前候选记录字段为 `japan_site`、`japan_url`、`japan_title`、`japan_price_jpy`、`japan_image_url` 和 `note`，见 `app/schemas.py` 的 `JapanCandidateCreate`。把实际查询、采集时间、状态、规格依据、排序理由和未知项放入 `note`，不要声称数据库中存在尚未实现的字段。
- Mercari 搜索、商品和参考店铺采集任务分别通过 `/api/japan/search`、`/api/japan/collect/item`、`/api/japan/collect/shop` 创建；采集后由 Agent 自主选择合格索引，使用 `/api/automation/jobs/{id}/import` 导入。导入前仍须按本文件过滤 `sold`、未知价、门槛不符和重复链接。
- 商品详情采集器现已从水合后的公开页面提取卖家主页 URL、卖家 ID 与显示名，支持从单品追到卖家主页；店铺采集可读取当前主页展示的商品卡片。独立的已售历史分页和递归卖家网络队列仍未实现，必须把本轮实际读到的售卖状态与扫描数量如实记录。

目前项目已有商品、卖家主页采集任务入口和参考店铺监控，但**尚无完整的卖家商品网络图、卖家经营类型判断、同商品跨卖家归并及递归扩展队列**。后续开发需在数据模型中区分卖家、规范化商品与 listing，并保存它们之间的带来源关系；已售 listing 应进入需求证据，不应作为当前库存。现有 `/api/automation/jobs/{id}/import` 只执行价格及重复记录检查，Agent 在导入店铺页结果前还须检查售卖状态，并将已售状态写入候选备注。

## 选品资料包字段

每个合格候选都要能说明“为什么是这个商品、为什么值得进入下一阶段”，而不是只保存一条标题和价格。标准资料包应保留：

- **搜索依据**：用户原始主题、实际使用的日文查询词、采集时间与站点。
- **商品身份**：日本原标题、原始商品链接、已证实的品牌/系列/型号/版本、规格或套装数量、成色；未知字段保持未知。
- **页面证据**：页面标价及币种、在售/售罄状态、主图链接、实际页面可见的卖家/热度信息及证据来源。
- **选品结论**：是否满足硬条件、相对排序、具体证据、主要风险/未知项，以及方便中国找货的商品识别词。
- **分类与刊登属性**：规范商品类型和建议的 Mercari 分类叶节点；记录材质、型号、尺寸/尺码、颜色、容量、版本、套装数量、兼容性和每个变体库存等实际存在的属性。每个值都附来源链接或原文依据；不适用的属性省略，未知属性明确写未知。服装必须保留“尺码/颜色 → 库存”矩阵，不能只记一个总件数。

当前 `JapanCandidateCreate` 只持久化平台、商品链接、原标题、日元价格、参考图和自由备注；商品类型与其他证据仍须暂存备注，不要声称它们已写入独立字段。上架草稿另有 `category_attributes` JSON，可将从日本商品页 / 已确认中国货源获得的分类字段值连同来源依据传给 Mercari Shops 表单适配器。后端后续应把查询、规范化身份属性、变体矩阵、在售证据、热度信号及其采集时间、决策理由和不确定性拆成可追溯字段，并通过兼容迁移与 API schema 一起更新。

## 分类驱动的上架字段

Mercari Shops 分类会改变商品表单的专属字段，不能拿上次手办分类作为全品类模板。先从当前分类树确定实际叶节点；选好分类后再读取店铺表单出现的动态字段、必填标记和可选项。按表单控件名称或可见日文标签，将有来源依据的值放进草稿 `category_attributes`，例如：

```json
{
  "attributes.material": {
    "value": "PVC",
    "source": "中国货源详情",
    "evidence": "商品说明明确写明材质 PVC"
  }
}
```

适配器目前可扫描动态字段并自动填写匹配的原生输入框、下拉框、单选和复选项。值缺失、控件不支持或平台选项不一致时，必须报告字段名、必填状态和平台选项，保留到草稿核对流程；不得猜材质、尺码等事实。该机制是通用字段发现/映射基础，不代表所有 Shops 类别和复杂变体表单都已验证。
